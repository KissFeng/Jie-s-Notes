## 三、概念解释题

共 10 题，每题 3 分。

### 1. 请解释 Spring Boot 的“自动配置（Auto-configuration）”是什么，并说明它给项目开发带来的好处。

> **参考答案：**
> - **概念**：Spring Boot 根据类路径中引入的依赖（Starter）和 `@Conditional` 条件注解，在应用启动时自动扫描并按需向容器装配默认 Bean 与基础配置。
> - **好处**：
>   1. 遵循“约定优于配置”，大幅减少繁琐的 XML 和样板配置代码；
>   2. 开箱即用，显著提升项目搭建与开发效率；
>   3. 支持通过 `application.yml` 或自定义 Bean 覆盖默认配置，兼顾灵活性。

### 2. 请解释 Spring 的“控制反转（IoC）”与“依赖注入（DI）”，并说明这样设计给项目带来什么好处。

> **参考答案：**
> - **控制反转（IoC）**：将对象的创建、组装与生命周期管理权从业务代码反转交给 Spring 容器统一管理。
> - **依赖注入（DI）**：IoC 的具体实现方式，由容器在运行时通过构造器、Setter 或字段将所依赖的对象自动注入到目标组件中。
> - **好处**：
>   1. 降低模块间耦合度，面向接口编程，便于扩展与替换实现；
>   2. 便于单元测试（可轻松使用 Mock 对象替代真实依赖）；
>   3. 统一管理 Bean 生命周期与作用域，提升代码可维护性。

### 3. 请解释什么是 RESTful，并说明设计 RESTful 接口时应遵循哪些基本规范。

> **参考答案：**
> - **概念**：RESTful 是一种基于 HTTP 协议、面向资源的 Web API 设计风格，将服务端数据抽象为资源，通过统一接口对资源进行操作。
> - **基本规范**：
>   1. **URI 表示资源**：使用名词复数（如 `/api/v1/sensors`），路径中不使用动词；
>   2. **HTTP 方法表示动作**：`GET` 查询、`POST` 新增、`PUT/PATCH` 修改、`DELETE` 删除，保证 `GET/PUT/DELETE` 幂等；
>   3. **规范使用状态码**：如 `200` 成功、`201` 创建成功、`400` 参数错误、`401/403` 未认证/无权限、`404` 不存在、`500` 服务端错误；
>   4. **无状态与统一格式**：请求自包含认证信息（如 JWT），统一返回 JSON 格式数据。

### 4. 请解释什么是 JWT 无状态认证，并说明它与基于 Session 的认证方式的主要区别。

> **参考答案：**
> - **概念**：JWT（JSON Web Token）是由 `Header.Payload.Signature` 三部分组成的自包含令牌。用户登录后服务端签发令牌，后续请求携带该令牌，服务端仅通过校验签名即可确认身份，无需保存会话状态。
> - **与 Session 的主要区别**：
>   1. **状态存储**：Session 保存在服务端（内存或 Redis，有状态）；JWT 保存在客户端（服务端无状态）；
>   2. **水平扩展**：Session 在集群部署时需做会话共享；JWT 天然支持多实例横向扩展；
>   3. **注销控制**：Session 可在服务端随时删除立即失效；JWT 过期前无法直接作废，需借助黑名单或短有效期策略；
>   4. **安全传输**：JWT 的 Payload 仅做 Base64Url 编码（未加密），不可存放密码等敏感信息。

### 5. 请解释 Web 应用中的分层架构，并说明 Controller、Service、Mapper 三层各自的职责与依赖方向。

> **参考答案：**
> - **概念**：分层架构按职责将应用划分为多个逻辑层次，每层只关注自身任务并通过接口协作，实现关注点分离与高内聚、低耦合。
> - **各层职责**：
>   1. **Controller（控制层）**：接收 HTTP 请求、参数绑定与校验（`@Valid`）、调用 Service 并封装统一响应；
>   2. **Service（业务层）**：实现核心业务规则、流程编排、缓存/消息协调及事务控制（`@Transactional`）；
>   3. **Mapper（数据访问层）**：负责与数据库交互，执行增删改查 SQL 及结果映射。
> - **依赖方向**：单向向下依赖，即 `Controller → Service → Mapper`（避免跨层调用和反向依赖）。

### 6. 请解释缓存穿透、缓存击穿和缓存雪崩的区别，并分别说明一种应对措施。

> **参考答案：**
> 1. **缓存穿透**：大量请求查询**缓存和数据库中都不存在**的数据，请求直达数据库。**应对**：使用布隆过滤器拦截非法 Key，或对空结果缓存短 TTL。
> 2. **缓存击穿**：**单个热点 Key** 突然过期，瞬时大量并发请求同时打到数据库重建缓存。**应对**：使用互斥锁（分布式锁）控制单线程回源重建，或设置热点 Key 逻辑过期异步更新。
> 3. **缓存雪崩**：**大量 Key 同一时间集中过期**或 Redis 宕机，导致海量请求瞬间压垮数据库。**应对**：为过期时间增加随机偏移量分散失效（并结合 Redis 高可用集群与限流降级）。

### 7. 请解释消息队列的“削峰填谷”作用，并说明消费能力不足时可以采取哪些措施。

> **参考答案：**
> - **削峰填谷**：在突发高并发时，先将大量请求快速写入消息队列缓冲（削峰），避免直接压垮数据库；消费者再按自身处理能力平稳持续地消费处理（填谷），保障系统稳定。
> - **消费能力不足的应对措施**：
>   1. **水平扩展消费者**：增加消费者实例数或提高并发消费线程数；
>   2. **优化单条消费性能**：采用批量消费、批量入库及 SQL/索引优化；
>   3. **合理限流预取**：设置合适的 `prefetch` 预取数量，防止单消费者内存积压；
>   4. **降级与死信隔离**：拆分非核心逻辑，异常消息转入死信队列（DLQ）避免阻塞主队列。

### 8. 请解释 Spring AOP 的核心概念，并说明它在企业级项目中的典型应用场景。

> **参考答案：**
> - **核心概念**：AOP（面向切面编程）通过动态代理将横切关注点（通用非业务逻辑）与核心业务解耦，统一织入目标方法执行前后。核心组成包括**切面（Aspect）**、**切点（Pointcut）**、**连接点（JoinPoint）**和**通知（Advice）**。
> - **典型应用场景**：
>   1. 声明式事务管理（`@Transactional`）；
>   2. 统一操作日志记录与接口耗时监控；
>   3. 统一权限校验与安全控制；
>   4. 统一限流、防重提交与缓存处理（`@Cacheable`）。

### 9. 请解释 Spring 事务的传播行为，并举例说明 REQUIRED 与 REQUIRES_NEW 的区别。

> **参考答案：**
> - **传播行为**：指当一个事务方法调用另一个事务方法时，事务如何在方法之间传递、复用或隔离的规则。
> - **`REQUIRED` 与 `REQUIRES_NEW` 的区别**：
>   1. **`REQUIRED`（默认）**：若当前存在事务则加入该事务，否则新建事务。内外方法共享同一事务，任一异常都会整体回滚（例：下单调用扣减库存，库存扣减失败时订单一并回滚）。
>   2. **`REQUIRES_NEW`**：挂起当前事务并开启一个全新独立事务。内层事务的提交或回滚与外层互不影响（例：业务操作中记录审计/告警日志，外层业务回滚时日志仍能独立保存）。

### 10. 请解释 RBAC 模型，并说明在 Spring Security 中落地 RBAC 的基本思路。

> **参考答案：**
> - **RBAC 概念**：基于角色的访问控制（Role-Based Access Control），通过“**用户 ↔ 角色 ↔ 权限**”三层关联，将权限授予角色、再将角色分配给用户，实现权限的解耦与集中管理。
> - **Spring Security 落地思路**：
>   1. **数据建模**：建立用户、角色、权限及对应的多对多关联表；
>   2. **加载权限**：实现 `UserDetailsService`（或 JWT 过滤器），查询用户角色（`ROLE_xxx`）与权限标识，封装为 `GrantedAuthority` 存入 `SecurityContext`；
>   3. **配置鉴权**：在 `SecurityFilterChain` 中配置路径访问控制，并开启 `@EnableMethodSecurity`，通过 `@PreAuthorize("hasRole(...)/hasAuthority(...)")` 实现接口级细粒度鉴权。

### 1. 项目组对新同事小张提交的“农事管理”模块做代码评审，发现 FarmingController 里既有权限判断、业务计算，也直接写了 SQL 查询数据库，而 FarmingService 里只有一行方法转发。若你是评审人，请指出这段代码存在的两个问题，并说明 Controller、Service、Mapper 三层各自应承担什么职责。

> **参考答案：**
> - **存在的两个问题**：
>   1. **职责混乱，违背单一职责与分层原则**：Controller 承担了权限判断、业务计算与直接 SQL 查询，代码臃肿且难以复用和单测；
>   2. **Service 层空心化与跨层强耦合**：Service 沦为无效转发，Controller 越层操作数据库，导致事务边界无法统一管理、后续维护成本高。
> - **三层各自职责**：
>   1. **Controller 层**：只负责接收请求、参数绑定与校验（`@Valid`）、调用 Service、封装统一返回结果（权限校验交由 Spring Security/注解处理）；
>   2. **Service 层**：负责核心业务计算、流程编排与事务控制（`@Transactional`）；
>   3. **Mapper 层**：专注数据库访问与 SQL 执行，向 Service 提供数据读写能力。

### 2. SmartAG 的设备状态数据（在线/离线、最近心跳时间）查询频繁、修改较少。项目组用 Redis 缓存了设备状态，TTL 为 10 分钟。运维人员在管理端把某台设备手动标记为“维护中”后，设备列表仍显示“在线”，直到 TTL 到期。请分析原因，并给出兼顾一致性与性能的缓存更新方案。

> **参考答案：**
> - **原因分析**：系统只依赖 Redis 的被动过期（TTL 10 分钟），在管理端更新数据库设备状态时未同步删除或更新对应缓存，导致 TTL 到期前查询一直命中旧数据。
> - **缓存更新方案**：
>   1. **采用 Cache Aside（旁路缓存）策略**：修改设备状态时，**先更新数据库，再删除对应的 Redis 缓存**，下次查询自动回源加载最新状态并重建缓存；
>   2. **保留合理 TTL 兜底**：继续设置过期时间（如 5–10 分钟并加随机偏移），避免偶发删缓存失败造成长期脏数据；
>   3. **高一致性增强（可选）**：对关键状态变更可结合延迟双删或消息队列异步重试删缓存，保证最终一致性。

### 3. 系统上线后，每天 8:00—9:00 管理端“传感器实时数据”页面响应明显变慢，其他时段正常。请依据 GB/T 28827.1—2022 的运行监控要求，说明你会查看数据库、缓存和应用三侧的哪些监控指标，以及如何判断瓶颈位置。

> **参考答案：**
> - **三侧核心监控指标**（依据 GB/T 28827.1—2022 运行监控与性能分析要求）：
>   1. **数据库侧**：QPS/TPS、慢查询数量与耗时、连接池活跃/等待连接数、CPU/磁盘 I/O 及锁等待；
>   2. **缓存侧（Redis）**：缓存命中率、命令响应耗时、内存使用率与淘汰数、连接数及慢日志；
>   3. **应用侧（Spring Boot / Actuator）**：接口 RT（P95/P99）、Tomcat 线程池活跃/排队数、JVM 内存与 GC 频率/停顿时间、CPU 利用率及定时任务执行日志。
> - **瓶颈判断方法**：
>   1. 对比 8:00—9:00 与正常时段的指标变化，同时排查该时段是否有集中定时任务或上班高峰查询；
>   2. 若**缓存命中率骤降**，说明存在缓存失效/穿透回源；
>   3. 若**数据库慢查询激增、连接池打满或 CPU/I/O 飙升**，瓶颈在数据库；若数据库与缓存正常而**应用侧 GC 频繁或线程池耗尽**，瓶颈在应用层计算或外部调用阻塞。

### 4. SmartAG 每分钟接收约 3000 条传感器上报数据。早期版本在上报接口中同步判断阈值并写库， 高峰期接口超时。改造后接口只把数据发送到 RabbitMQ，由消费者异步入库。请说明改造后请求为什么不再堆积，以及消费者处理能力不足时可以采取哪些措施。

> **参考答案：**
> - **请求不再堆积的原因**：
>   1. **异步解耦**：上报接口只需完成参数校验并将消息发送到 RabbitMQ 即可立即返回（毫秒级），不再同步阻塞等待阈值计算和写库；
>   2. **削峰填谷**：RabbitMQ 作为缓冲队列吸收瞬时高峰流量，快速释放 Tomcat 线程，避免连接占满和接口超时。
> - **消费者处理能力不足的应对措施**：
>   1. **水平扩容与提高并发**：增加消费者实例数量，调大并发消费线程数；
>   2. **批量消费与批量入库**：改为攒批消费与 Batch Insert，显著降低数据库写 I/O；
>   3. **限流与预取控制**：合理设置 `prefetch` 并使用手动 ACK，防止单节点积压 OOM；
>   4. **逻辑与存储优化**：优化表索引/分表，非核心逻辑拆出异步处理，异常消息转死信队列。

### 5. SmartAG 后端计划部署 3 个实例，并通过 Nginx 做负载均衡。登录状态若继续使用 HttpSession， 需要额外解决会话共享问题。请从状态存储、水平扩展、注销与安全四个角度比较 Session 与 JWT，并给出选型建议。

> **参考答案：**
> - **四角度比较**：
>   1. **状态存储**：Session 存储在服务端（内存或 Redis）；JWT 将认证信息签发给客户端保存，服务端无状态；
>   2. **水平扩展**：Session 在多实例下需依赖 Redis 共享会话或粘性会话；JWT 任意实例仅凭密钥即可验签，天然易水平扩展；
>   3. **注销控制**：Session 可在服务端直接销毁、立即生效；JWT 过期前默认无法主动失效，需配合黑名单或短有效期机制；
>   4. **安全性**：Session 仅传 SessionID，但需防 CSRF；JWT 放 Header 可避免 CSRF，但 Payload 未加密不可存敏感信息，需配合 HTTPS 并防 XSS 窃取。
> - **选型建议**：推荐采用 **JWT（短有效期 Access Token）+ Redis 黑名单 / Refresh Token** 方案，兼顾 3 实例无状态水平扩展能力与强制注销/安全可控性。

### 6. 设备阈值配置“读多写少”，但要求修改后尽快在所有实例生效。团队在 Redis 与本地 Caffeine 缓存之间犹豫。请比较两种方案的优缺点，并给出适合 SmartAG 的选型或组合方案。

> **参考答案：**
> - **两种方案对比**：
>   1. **Redis**：优点是全局共享、数据一致性强，修改后所有实例立即可见；缺点是每次读取有网络 I/O 开销，延迟高于本地内存且依赖 Redis 可用性。
>   2. **Caffeine（本地缓存）**：优点是纯内存访问、微秒级延迟、零网络开销；缺点是各实例内存隔离，某实例修改后其他实例无法及时感知，易出现数据不一致。
> - **选型/组合方案**：推荐 **Caffeine（L1 本地缓存）+ Redis（L2 分布式缓存）+ Redis Pub/Sub（或 RabbitMQ 广播）** 多级缓存方案：
>   - 读操作优先命中本地 Caffeine，未命中再读 Redis 并回填本地，兼顾高性能；
>   - 修改阈值时先更新数据库并更新/删除 Redis，再广播通知所有实例立即失效本地 Caffeine 缓存，同时设置较短 TTL 兜底，保证快速全实例生效。

### 7. SmartAG 需要把告警消息按“设备类型 + 告警级别”路由到不同消费者：温度/湿度告警分别处理，严重告警还要额外短信通知。请比较 Direct、Topic、Fanout 三种交换机的适用场景，给出选型并说明如何保证消息不丢失。

> **参考答案：**
> - **三种交换机适用场景**：
>   1. **Direct**：按 RoutingKey **精确匹配**路由，适合固定分类的点对点分发；
>   2. **Topic**：按通配符（`*` 匹配单个词、`#` 匹配零或多个词）**模式匹配**，适合多维度灵活路由；
>   3. **Fanout**：**广播**到所有绑定队列（忽略 RoutingKey），适合全量通知。
> - **选型方案**：选用 **Topic 交换机**，RoutingKey 设计为 `alarm.<设备类型>.<级别>`（如 `alarm.temp.critical`）：
>   - 温度队列绑定 `alarm.temp.*`，湿度队列绑定 `alarm.humidity.*`；
>   - 短信通知队列绑定 `alarm.*.critical`，自动捕获所有严重告警。
> - **保证消息不丢失的措施**：
>   1. **生产者确认**：开启 Publisher Confirm 与 Return 回调，确保消息成功到达交换机与队列；
>   2. **Broker 持久化**：交换机、队列（`durable=true`）及消息均开启持久化；
>   3. **消费者手动 ACK**：关闭自动确认，业务处理成功后再手动 `basicAck`，失败则重试或入死信队列。

### 8. SmartAG 目前是一个 Spring Boot 单体应用，包含设备管理、农事管理、告警、报表等模块。随着团队和需求增长，有人主张立即拆分为微服务。请结合项目现状，分析单体与微服务的利弊，并给出你的架构演进建议。

> **参考答案：**
> - **单体架构利弊**：
>   - 优点：开发、测试、部署与运维简单，模块间进程内调用零网络延迟，本地事务易保证；
>   - 缺点：规模扩大后模块易耦合、局部故障可能波及全局、难以按模块独立扩缩容。
> - **微服务架构利弊**：
>   - 优点：服务边界清晰、可独立发布与弹性扩缩容、故障隔离性好；
>   - 缺点：引入注册中心、配置中心、分布式事务、链路追踪与高运维成本，过早拆分会显著拖慢迭代效率。
> - **架构演进建议**：**不建议立即全面拆分**，应采取渐进式演进路线：
>   1. **短期（模块化单体）**：利用 Maven 多模块清晰划分设备、农事、告警、报表边界，做到高内聚低耦合、数据表逻辑隔离；
>   2. **中期（热点剥离）**：优先将高并发、资源特征差异大的模块（如传感器数据采集/告警消费或重计算报表）独立拆分部署；
>   3. **长期（按需微服务化）**：待业务量、团队规模和 DevOps/监控体系成熟后，再按业务域逐步演进为微服务。

public class SensorDataServiceImpl implements SensorDataService {
    @Autowired
    private SensorDataMapper sensorDataMapper;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;
    @Autowired
    private RabbitTemplate rabbitTemplate;

    // 数据库写入需保证事务原子性，失败时回滚数据库更改
    @   ⑤
    @Override
    public void save(Long deviceId, SensorDataDTO dto) {
        SensorData entity = new SensorData();
        entity.setDeviceId(deviceId);
        entity.setTemperature(dto.getTemperature());
        sensorDataMapper.insert(entity);

        // 写入 Redis，key 形如 smartag:sensor:1，5 分钟后过期
        stringRedisTemplate.opsForValue()
                .   ⑥   ("smartag:sensor:" + deviceId,
                        JSON.toJSONString(entity), 5, TimeUnit.MINUTES);

        // 发送到交换机 smartag.sensor.exchange，路由键 sensor.data
        rabbitTemplate.   ⑦ ("smartag.sensor.exchange",
                "sensor.data", JSON.toJSONString(entity));
    }

    // 查询某设备最近一条数据
    public SensorData getLatest(Long deviceId) {
        LambdaQueryWrapper<SensorData> qw = new LambdaQueryWrapper<>();

        // 查询条件：deviceId 等于传入值
        qw.   ⑧ (SensorData::getDeviceId, deviceId)
                .orderByDesc(SensorData::getCollectTime)
                .last("limit 1");
        return sensorDataMapper.selectOne(qw);
    }
}
